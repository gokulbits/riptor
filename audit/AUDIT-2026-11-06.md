# Riptor security and correctness audit — 2026-11-06

Scope: the whole workspace at `741713b` (version 0.1.8), on Windows with the
MinGW toolchain. Two halves: dependency advisories, and a code audit of the
paths that take hostile input. This doubles as the pre-release security review
`CLAUDE.md` asks for.

Nothing in product code was changed. The proof-of-concept tests live in
`crates/riptor-core/tests/audit_poc.rs` on the audit branch; each asserts the
**defective** behaviour that exists today, so `cargo test` stays green and the
assertion flips when the finding is fixed. Every one of them was run.

# Part 1 — Dependency advisories

Method: RustSec `advisory-db` cloned fresh into the scratchpad (never into the
repo) and matched against `Cargo.lock` (673 distinct crates) by package name
with the advisory's own `patched` / `unaffected` version requirements. Every hit
was then traced with `cargo tree -i` and the vulnerable function checked at its
call site. `cargo-deny` is not installed locally; CI runs it, so CI sees the
same set.

Five advisories match. **None is exploitable.**

### ringbuf 0.4.8 — RUSTSEC-2026-0293 — memory-corruption — fixed in 0.5.2

Double free / use-after-free in `Consumer::skip` and `Consumer::clear` when an
element's `Drop` panics.

Riptor reaches the vulnerable function: `librqbit-utp-0.7.0/src/stream_tx.rs:83`
calls `self.consumer.lock().skip(count)`, and `librqbit-utp` is a
non-optional dependency of the vendored librqbit, live whenever the listener
mode is `TcpAndUtp` (`engine.rs:3154`).

**Not exploitable.** The ring buffer is `SharedRb<Heap<u8>>`
(`stream_tx.rs:129`) — the element type is `u8`, whose `Drop` is a no-op and
cannot panic, so the advisory's precondition is unreachable. Riptor also cannot
fix it directly: `ringbuf` is a transitive dependency of the crates.io crate
`librqbit-utp`, which would have to bump it. Worth raising with librqbit
upstream when the fork is rebased; no action needed now.

### generic-array 0.12.4 and 0.14.7 — RUSTSEC-2020-0146 — unsound — no fixed version

The `arr!` macro can erase lifetimes.

**Not exploitable.** `arr!` is not used anywhere — not in Riptor, not in
`vendor/`, and not in any of the crates that pull `generic-array` in
(`size_format` 1.0.2 for 0.12.4; `aead`/`aes-gcm`/`crypto-common` and the
Argon2 and XChaCha20-Poly1305 stack for 0.14.7). There is no fixed release to
move to, and 0.12.4 arrives through `size_format`, a librqbit dependency.

### glib 0.18.5 — RUSTSEC-2024-0429 — unsound — fixed in 0.20.0

Unsoundness in the `Iterator` / `DoubleEndedIterator` impls for
`glib::VariantStrIter`.

**Not exploitable, Linux only.** It arrives under the GTK/webkit stack that
Tauri pulls in on Linux; Riptor never constructs a `VariantStrIter`. The version
is pinned by Tauri's own dependency tree, so it moves when Tauri does.

### Unmaintained, informational only

`proc-macro-error` 1.0.4 (RUSTSEC-2024-0370), `zbus_names` 3.0.0 / 4.3.5
(RUSTSEC-2026-0371), `zvariant` 4.2.0 / 5.15.1 (RUSTSEC-2026-0370),
`zvariant_derive` 4.2.0 / 5.15.1 (RUSTSEC-2026-0372). All transitive under
Tauri; no code defect, nothing to do beyond following Tauri upgrades.

### cargo update — the librqbit sibling trap is real

`cargo update --dry-run` would move 52 packages, and among them:

```
librqbit-buffers 9.0.1 -> 9.1.0
librqbit-clone-to-owned 9.0.1 -> 9.1.0
librqbit-sha1-wrapper 9.0.1 -> 9.1.0
librqbit-upnp 9.0.1 -> 9.1.0
```

That is exactly the split `CLAUDE.md` warns about — the vendored fork is 9.0.1.
A blanket `cargo update` must not be run. Pin those four, or update selectively
(`cargo update -p <crate>`) until the fork is rebased on 9.1.x.

patch-level: `rfd` 0.16.0 → 0.17.2, `typed-path` 0.12.4 → 0.13.0 and `zip`
9.0.5 → 9.4.1 (`zip` is used by `pyembed.rs` to unpack the embeddable Python,
so it is on a hostile-input path and the bump is worth taking deliberately).

# Part 2 — Code findings

## A3 — High — a `.torrent` with `piece length 0` aborts the process

**Where:** `librqbit-core-9.0.1/src/lengths.rs:88` (a crates.io dependency, not
vendored), reached through `Engine::preview` at
[engine.rs:404](crates/riptor-core/src/engine.rs:404).

```rust
// lengths.rs:84
pub fn new(total_length: u64, piece_length: u32) -> crate::Result<Self> {
    if total_length == 0 {
        return Err(Error::BadTorrentZeroLength);
    }
    let total_pieces = total_length.div_ceil(piece_length as u64) as u32;   // :88
```

`total_length` is guarded; `piece_length` is not. `TorrentMetaV1Info::validate`
calls `Lengths::from_torrent` before any of its own checks, so a torrent whose
`info` dict says `12:piece lengthi0e` divides by zero.

**Untrusted-input path.** `piece length` is attacker-controlled metadata.
Everything that adds or inspects a torrent goes through `Engine::preview` /
`Engine::add`: a `.torrent` file the user opens or drops, a URL or magnet add,
a `.torrent` fetched by an **RSS rule** (no user interaction at all once a feed
is configured), a multipart upload to the remote-control
`/api/v2/torrents/add`, a watched folder, and `import`. `riptor_core::input`
caps the file at 16 MiB but does not look at the piece length.

**Impact.** Release builds set `panic = "abort"`
([Cargo.toml](Cargo.toml:30)), so this is not a caught error — the whole
application terminates, losing all in-flight torrent state. From a hostile RSS
feed or a reachable remote-control port it is a remote, unauthenticated-in-
practice crash; a 59-byte file does it.

**Verified.** Both PoC tests pass:

- `a3_zero_piece_length_panics_instead_of_erroring` — the parse alone panics.
- `a3_zero_piece_length_reaches_engine_preview` — `Engine::preview` on the
  file panics, i.e. Riptor's own entry point is on the path.

Exact message, with the hook left in place:

```
thread '<unnamed>' panicked at librqbit-core-9.0.1\src\lengths.rs:88:41:
attempt to divide by zero
```

**Suggested fix.** Do not wait on upstream. Reject it in
`riptor_core::input` before any librqbit call, where the other metadata limits
already live — a torrent's piece length must be non-zero, and in practice a
power of two from 16 KiB to 64 MiB:

```rust
// in input.rs, next to MAX_TORRENT_BYTES
pub const MIN_PIECE_LENGTH: u32 = 16 * 1024;
pub const MAX_PIECE_LENGTH: u32 = 64 * 1024 * 1024;
```

and check `info.piece_length` against it on every parse. Add the case to
`crates/riptor-core/tests/hostile_input.rs`. An upper bound matters on its own:
`piece_length` is a `u32` and `webseed.rs:303` does
`Vec::with_capacity(len as usize)` per piece, while completed pieces are
buffered whole in memory, so a torrent claiming a 4 GiB piece forces multi-GiB
allocations. This is also the second librqbit crash worth the private upstream
report `CLAUDE.md` already tracks for the bencode bugs — note that
`librqbit-core` is not vendored, so Riptor cannot patch it in place.

## A1 — High — a forged backup enables unauthenticated, internet-exposed remote control

**Where:** [engine.rs:2041](crates/riptor-core/src/engine.rs:2041) (restore
applies settings), [settings.rs:234](crates/riptor-core/src/settings.rs:234)
(`WebUi::validate`).

`backup.rs` is explicit that a password-less backup is "tamper-evident, not
forgery-proof" — mode 0 is sealed with `APP_KEY`, a constant compiled into the
binary, so anyone can produce a backup Riptor accepts as genuine. `restore_backup`
is written with that in mind and strips plenty: `checksums`, `findings`,
`content_findings` and `queue_pos` are dropped, renames must pass
`clean_rel_path`, file indices are range-checked, tags revalidated, save folders
run through `check_root`.

Settings get none of that scrutiny:

```rust
// engine.rs:2041
if opts.settings {
    let s = payload.settings.clone();
    match s.validate().and_then(|_| self.check_root(&s.download_dir)) {
        Ok(()) => { self.update_settings(s).await?; report.settings_restored = true; }
```

`WebUi::validate` only checks shapes — port ≥ 1024, the address parses, the
username is printable, the CIDRs parse, the ban numbers are in range. Nothing
constrains what the settings *mean*.

**Untrusted-input path.** The user opens a `.riptorbackup` they were sent (the
normal way to move settings between machines) and leaves "settings" ticked. The
forged payload sets:

```
web_ui.enabled          = true
web_ui.bypass_localhost = true
web_ui.bypass_subnets   = true
web_ui.subnet_whitelist = ["0.0.0.0/0", "::/0"]
web_ui.allow_public     = true
web_ui.upnp             = true
web_ui.csrf_protection  = false
```

`parse_cidr("0.0.0.0/0")` is valid, and `cidr_contains` with 0 bits builds a
zero mask (`settings.rs:222`, `checked_shl(32).unwrap_or(0)`), so it matches
every client. `Ctx::bypassed` (`api.rs:112`) then returns true for every
address, and `signed_in` short-circuits to true before any password or API key
is looked at. `allow_public` stops `net::Gate` refusing non-local clients, and
`upnp` asks the router to forward the port.

**Impact.** Restoring one file hands an attacker full, unauthenticated control
of the victim's client from the internet — add and remove torrents, read and
change the save path, enumerate the filesystem through the API's save-path
handling, drive downloads into any folder `check_save_root` allows. No password
is in the backup (`webui-auth.json` is deliberately excluded), so the bypass
*is* the authentication. The UI's restore summary does not single any of this
out.

**Verified.** `a1_forged_backup_enables_unauthenticated_remote_control` passes:
it seals a hostile `Settings` with no password, confirms
`is_password_protected` is false, starts a real `Engine`, restores, and asserts
the live settings came back with all of the above set.

**Suggested fix.** Treat the remote-control block the way the record fields are
already treated — as untrusted, and drop the dangerous parts rather than trying
to validate them. In `restore_backup`, before `update_settings`:

```rust
// A forged backup must never be able to open a door.
let keep = self.settings().web_ui.clone();
s.web_ui = WebUi { /* restore only cosmetic fields */ ..keep };
```

At minimum force `enabled`, `bypass_localhost`, `bypass_subnets`,
`allow_public`, `upnp`, `reverse_proxy` and `trusted_proxies` back to the
running values, and add a line to `RestoreReport.skipped` saying remote-control
settings were not restored. The same reasoning applies to `ddns` (which carries
an update URL) and to `cert_file` / `key_file`. A second, weaker layer: refuse
to restore settings at all from a backup that was not password-protected, and
say so in the UI.

## A2 — Medium — `check_save_root` is lexical, so protected folders are reachable by another spelling

**Where:** [paths.rs:93](crates/riptor-core/src/paths.rs:93), with
`normalize` at `paths.rs:18` and `starts_with` at `paths.rs:32`.

`check_save_root` is the single gate every save folder goes through — add,
category, settings, restore — and `CLAUDE.md` names it as such. It normalises
`.` and `..` textually and lowercases for the Windows comparison, but never
canonicalises, so any other spelling of the same directory passes.

**Confirmed bypasses** (`a2_check_save_root_misses_windows_path_aliases`,
passing, which asserts the defect):

- `\\?\C:\Windows\System32` — **accepted**. `normalize` keeps the
  `VerbatimDisk` prefix, so the string is `\\?\c:\windows\system32`, which does
  not start with `c:\windows`. The plain `C:\Windows\System32` is correctly
  refused, so this is purely a spelling gap. `\\.\C:\...` is the same.
- `C:\PROGRA~1\...` — the 8.3 short name for `C:\Program Files`, **accepted**.
  Short names resolve on this machine's volume (checked), so this reaches
  Program Files.
- UNC paths (`\\server\share\...`) are not covered by any protected root; a save
  folder pointing at an admin share such as `\\127.0.0.1\C$\Windows` is
  accepted.

On Unix (`a2_check_save_root_does_not_resolve_symlinks`) a symlink is not
resolved either: a save folder that is a symlink to `/etc` is accepted.

**Untrusted-input path.** Two. A forged backup (see A1) can set
`download_dir`, a category folder or `move_on_complete` to any of these
spellings — restore calls `check_root` and it returns `Ok`. And over
remote control, `/api/v2/torrents/add` passes `savepath` straight into
`AddParams` (`api.rs:941`), reaching the same check.

**Impact.** Torrent data written into `C:\Windows\System32`, `Program Files` or
`/etc` — the exact outcome the check exists to prevent. Writes still need the
privileges for the target, so on a standard account this is mostly a
defence-in-depth failure; on an account that can write to those folders it is
how you get a file where the OS will trust it. Severity is Medium rather than
High because the dangerous spelling has to arrive from somewhere, which in
practice means A1 or an enabled remote-control port.

**Related, same root cause.** `safe_join` (`sanitize.rs:91`) is also lexical.
It is sound for its own job — components are rebuilt from scratch and every one
must be `Component::Normal` — but if a *directory* inside an otherwise valid
save root is a symlink or junction, the join stays under the root textually
while the write lands elsewhere. Riptor's storage never creates links, so this
needs a local process to plant one.

**Suggested fix.** Canonicalise before comparing, falling back to the lexical
path only for the part that does not exist yet:

```rust
// paths.rs, in check_save_root
let n = normalize(p);
// Resolve the deepest existing ancestor, so junctions and 8.3 names collapse.
let real = deepest_existing(&n).and_then(|a| a.canonicalize().ok());
```

then test both `n` and the canonical form against `protected_roots`, and
canonicalise each protected root the same way. On Windows `canonicalize`
returns a `\\?\` path, so strip that prefix on both sides rather than comparing
mixed forms. Separately, reject `Component::Prefix` kinds that are not
`Disk` — verbatim, UNC and device paths have no business being a save folder —
and add the three Windows spellings plus the symlink case to the `paths.rs`
tests.

## A4 — Low — `move_files` checks the destination, then overwrites it

**Where:** [relocate.rs:20](crates/riptor-core/src/relocate.rs:20) and
[relocate.rs:50](crates/riptor-core/src/relocate.rs:50).

The module header promises "existing targets are never overwritten", and
`move_files` checks `!to.exists()` for every pair up front. The moves then
happen in a second loop, and `fs::rename` silently replaces an existing
destination on both Windows and Unix. The cross-device branch is the same:
`fs::copy(from, to)` truncates whatever is there.

**Untrusted-input path.** Thin. The window is between the check loop and each
rename, and the destination is inside a validated save root, so whoever plants
the file there already has write access to that folder. It is also reachable
without an attacker: two concurrent moves, or the user creating the file in the
window.

**Impact.** A file in the save folder is destroyed where the code says it will
not be. Not a privilege boundary, but the guarantee is stated and does not hold.

**Suggested fix.** Make the no-overwrite atomic instead of checked-then-done.
On Unix use `rustix::fs::renameat_with(..., RenameFlags::NOREPLACE)` and fall
back to `link`+`unlink` where the filesystem lacks it; on Windows use
`MoveFileExW` without `MOVEFILE_REPLACE_EXISTING` (which is the default) rather
than `fs::rename`, which passes the replace flag. For the copy branch, open the
destination with `create_new(true)`. Keep the up-front check for the early,
friendly error.

## A5 — Low — `unsafe` is not actually denied in the `riptor` crate

**Where:** [src-tauri/src/lib.rs:1](src-tauri/src/lib.rs:1).

`CLAUDE.md` restricts `unsafe` to four places, and the audit confirms the code
honours it exactly — the only `unsafe` outside `vendor/` is in
`riptor-storage/src/os.rs`, `src-tauri/src/associations.rs`,
`src-tauri/src/elevate.rs` and the vendored `bind_device` patch. Every other
crate enforces it:

```
riptor-core, riptor-daemon, riptor-net, riptor-rss, riptor-search,
riptor-vpn, riptor-vpn-helper   ->  #![forbid(unsafe_code)]
riptor-storage                  ->  #![deny(unsafe_code)]  + per-fn allow
```

`src-tauri/src/lib.rs` has **no** `deny`/`forbid` attribute. The
`#[allow(unsafe_code)]` attributes in `associations.rs:141` and `elevate.rs:46,
91, 111, 384` are therefore decorative — they suppress a lint that is not on.
A new `unsafe` block anywhere in the `riptor` crate compiles silently, even
under `cargo clippy -D warnings`.

**Impact.** No defect today; the invariant simply is not mechanically enforced
in the one crate that is allowed exceptions to it, and that crate holds the UAC
elevation code.

**Suggested fix.** Add `#![deny(unsafe_code)]` to `src-tauri/src/lib.rs`. The
existing per-function `#[allow(unsafe_code)]` attributes then start doing the
job they were written for, and nothing else needs to change.

**Soundness of the four permitted sites — reviewed, all sound.**
`os.rs` zeroes a `MEMORYSTATUSEX` (valid all-zero, `dwLength` set before the
call), passes a NUL-terminated wide buffer that outlives `GetDiskFreeSpaceExW`,
and calls `DeviceIoControl` for `FSCTL_SET_SPARSE` with no buffers; all three
check the return and use `last_os_error`. `associations.rs:145` passes the
documented null items to `SHChangeNotify`. `elevate.rs` zeroes a
`SHELLEXECUTEINFOW`, closes the `ShellExecuteExW` handle exactly once in
`Drop`, and in `attach` runs only `setsid` and `ioctl_tiocsctty` inside
`pre_exec` — both async-signal-safe and allocation-free, with the slave fd held
open by the caller until exec. The vendored `bind_device` patch sets
`IP_UNICAST_IF` / `IPV6_UNICAST_IF` on a borrowed socket.

## A6 — Low — the elevated Windows helper trusts `SystemRoot` and `ProgramData` from its caller

**Where:** [riptor-vpn-helper/src/main.rs:290](crates/riptor-vpn-helper/src/main.rs:290)
(`private_dir`, `ProgramData` and the `icacls.exe` path),
and `main.rs:255` (`stop_previous`, `tasklist.exe` / `taskkill.exe`).

The helper runs elevated. It locates Windows binaries through environment
variables:

```rust
let base = std::env::var_os("ProgramData").map(PathBuf::from)
    .unwrap_or_else(|| r"C:\ProgramData".into());
...
let icacls = Path::new(&std::env::var_os("SystemRoot")
    .unwrap_or_else(|| r"C:\Windows".into()))
    .join("System32").join("icacls.exe");
```

A UAC-elevated child launched through `ShellExecuteExW` inherits the caller's
environment, so whoever starts the helper chooses which `icacls.exe`,
`tasklist.exe` and `taskkill.exe` the elevated process executes, and where the
"private" directory lives.

**Impact and honest limits.** Exploiting it requires getting past the UAC
prompt, so it is not a path from a standard user to admin — it is the familiar
"admin-group user clicks through consent" case that Microsoft does not treat as
a boundary. It is still the wrong shape for a binary whose whole job is to be a
privilege boundary, and the fix is two lines. Redirecting `ProgramData` is less
interesting than it looks: the attacker supplies the config and the management
password anyway, and the worst `stop_previous` will do with a planted PID file
is `taskkill` a process whose image name is already `openvpn.exe`.

The good parts, for the record: `openvpn_exe()` never consults `PATH` and
resolves through `HKLM\SOFTWARE\OpenVPN` (admin-writable only) with a hardcoded
fallback; the management password must be 16+ ASCII alphanumerics, which stops
the `pw_file` argument being used as a general file-read oracle; `open_alive`
requires an absolute path whose filename is exactly `vpn-alive.lock` and uses
`symlink_metadata` to insist on a plain file (the remaining TOCTOU is harmless —
the handle is only ever `lock_shared`'d); the Linux `private_dir` is a
hardcoded `/run/riptor-vpn` created 0700 with a post-creation symlink check in
the right order. On Linux pkexec scrubs the environment, so none of this
applies there.

**Suggested fix.** Resolve the system directory with
`GetSystemDirectoryW` instead of `%SystemRoot%`, and build the ProgramData path
from `SHGetKnownFolderPath(FOLDERID_ProgramData)` instead of the environment
variable — or simply hardcode `C:\Windows\System32` and `C:\ProgramData` rather
than preferring the environment and falling back to them.

**One more note, Linux.** `read_small(config, ...)` reads the config as root
and `OvpnError::Unsupported` puts the line's first token in the message, which
reaches Riptor's log as the unprivileged user (`CLAUDE.md`: pkexec's stderr goes
to the Logs view). Pointing the helper at `/etc/shadow` would echo a line of it.
This is not an escalation — it needs the same pkexec authorisation that would
let you read the file directly — but truncating or omitting the token in that
error would cost nothing.

## A7 — Low — the Linux plugin sandbox keeps loopback network access

**Where:** [riptor-search/src/nova.rs:175](crates/riptor-search/src/nova.rs:175).

The bubblewrap invocation is otherwise tight — `--ro-bind / /`, `--dev`,
`--proc`, `--tmpfs /tmp`, `--tmpfs $HOME` (which masks Riptor's data directory,
and with it `webui-auth.json` and the sealed history), the plugin directory
read-only, `--unshare-all --die-with-parent --new-session`, and Python run
with `-I -X utf8 -B` under `env_clear()` with eight variables let back in.

But `--share-net` undoes the network namespace, which plugins need. A hostile
plugin therefore reaches `127.0.0.1`, including Riptor's own remote-control
port. Chained with `bypass_localhost`, that is full torrent control for
third-party Python code.

**Honest limits.** Both doors must already be open: remote control is
`enabled: false` by default and `bypass_localhost: false`
(`settings.rs:168,176`). `CLAUDE.md` already notes a plugin can bypass the
proxy by opening its own sockets; this is the same gap pointed inward. Note too
that `manager.rs:253` reports `sandboxed: true` whenever `bwrap` is on PATH,
which is accurate about bubblewrap but reads as stronger containment than
`--share-net` provides — and **on Windows there is no sandbox at all**
(`nova.rs:188` runs Python directly), so plugins there have the user's full
privileges. That is disclosed through the `sandboxed` flag rather than
overclaimed, which is the right call; it is worth keeping the UI wording blunt.

**Suggested fix.** Keep `--share-net` but take loopback away: run the plugin in
its own network namespace with only the proxy reachable, or add an
`--unshare-net` plus a slirp-style helper. Cheaper interim measure: bind the
plugin proxy to a Unix socket and refuse plugin-originated connections to
loopback ports in `riptor_net::stays_local`. Cheapest: say in the Search
settings that a plugin can reach services on this machine.

## A8 — Info — `host_validation` is on by default but matches everything

`server_domains` defaults to `"*"` (`settings.rs:186`) and `host_allowed`
(`api.rs:137`) wildcard-matches it against any `Host`, so the default
configuration validates nothing. IP literals and `localhost` always pass by
design. This matches qBittorrent's default and is not a defect, but a user who
sees "Host header validation: on" is getting less than they think. Consider
defaulting `server_domains` to empty with IP-and-localhost still allowed, so
turning the toggle on does something.

Also minor, same file: `same_origin` compares host and port but not scheme, and
`auth/logout` is handled before the `signed_in` check in `dispatch`
(`api.rs:380`), so a cross-site request can log the user out when
`csrf_protection` is off.

## A9 — Info — the global sign-in pause is a lockout primitive

`Throttle::reserve` pauses password sign-ins for everyone once 30 failures
accumulate in an hour (`auth.rs:286`, `GLOBAL_FAILURES`), and the pause applies
even to the correct password. That is a deliberate trade — it is the only thing
that stops guessing spread across many addresses — but it means anyone who can
reach the port can keep the owner locked out of password login indefinitely at
30 failures an hour. The owner keeps the API key, which is explicitly exempt
(`api_key_from` falls through on `Login::Paused` because a 192-bit key cannot
be guessed; that reasoning is sound, though it does mean key attempts during a
pause are neither counted nor rate-limited). Worth a sentence in the UI so a
locked-out owner knows to use the API key, and worth considering an exemption
for clients that have signed in successfully before.

# Areas checked and found sound

Stated explicitly so this doubles as the pre-release review.

**`riptor-storage` path handling — sound.** `sanitize_component`
(`sanitize.rs:50`) replaces control characters, the Windows-forbidden set, and
the bidi overrides that make `photo<U+202E>gnp.exe` read as `photo.png`; trims
leading spaces and trailing dots and spaces; prefixes reserved device names,
matching Windows' own `CON.txt` behaviour by splitting on the first `.`;
truncates to 255 bytes on a char boundary while keeping a short extension, and
re-trims afterwards because truncating can expose a new trailing dot. It can
never return empty, `.` or `..`. `sanitize_relative` rebuilds every component
and then asserts the count did not collapse, which is what closes the Windows
`C:x` drive-prefix escape that librqbit still has. `safe_join` requires an
absolute root, `Component::Normal`-only relatives, and re-checks `starts_with`.
`dedupe` is case-insensitive and handles post-sanitising collisions. A 2000-case
proptest covers the single-component and under-the-root invariants. The one
gap is the lexical comparison noted under A2.

**Bencode caps — sound and correctly placed.** `MAX_DEPTH = 64` is enforced in
`enter()`, called from both `deserialize_seq` and `deserialize_map`
(`deserialize.rs:381,412`), and `deserialize_any` dispatches `l`/`d` through
those two rather than recursing itself — so the cap covers the dynamic path that
peers' extended handshakes use, which is where the original stack overflow was.
The depth counter is decremented on the error path too. Integer and string
lengths go through atoi's checked parsers. `raw_value.rs` contains no recursive
skip that could sidestep the counter. The existing
`hostile_input.rs::deep_nesting_is_refused` runs on a 256 KiB stack, which is
the right way to test it.

**Vendored patches match `vendor/PATCHES.md` — no undocumented patch.** Every
file carrying a `// RIPTOR PATCH:` marker appears in the document's tables:
bencode `deserialize.rs`; dht `dht.rs`, `lib.rs`, `resolve_hook.rs`;
dualstack-sockets `Cargo.toml`, `bind_device.rs`; tracker-comms `lib.rs`,
`observe.rs`, `resolve_hook.rs`, `tracker_comms.rs`, `tracker_comms_http.rs`;
librqbit `Cargo.toml`, `lib.rs`, `mse.rs`, `peer_connection.rs`, `read_buf.rs`,
`riptor_observe.rs`, `session.rs`, `session_persistence/json.rs`,
`storage/mod.rs`, `stream_connect.rs`, `torrent_state/initializing.rs`,
`torrent_state/live/mod.rs`, `torrent_state/mod.rs`. The four markers in
`stream_connect.rs` are all the MSE/PE row, as documented.

**OpenVPN profile sanitizer — sound.** `ovpn::sanitize` is a default-deny
allowlist: unknown options are refused rather than dropped, every file-argument
option is refused outright (including `config`, so nested inclusion is
impossible), script and routing options are stripped, inline blocks are limited
to seven certificate tags with bodies restricted to printable ASCII and an
exact `</tag>` terminator, and arguments must pass `safe_token` — which excludes
quotes and backslashes, so `emit`'s quoting cannot be escaped. `words()` is
line-scoped, so no newline injection. The profile must be a client, must have a
`remote`, must have an inline `<ca>`, and `dev` must start with `tun`. `APP_ONLY`
is appended **last**, so its `script-security 1`, `route-nopull`, the four
`pull-filter ignore` lines and the metric-9999 default route win over anything
in the profile; the helper also passes `--script-security 1` on the command
line. Leading `--` is stripped before the allowlist check, so `--up` lands in
the default-deny branch.

**Remote-control authentication — sound, and carefully built.** Argon2id at the
OWASP baseline with a per-password salt; parameters read back from
`webui-auth.json` are refused unless they are in the range Riptor itself
writes, so a forged file cannot make each check expensive (`load`, `auth.rs:160`,
with a test). Constant-time comparison via `same()`, used for the password hash,
the API key's SHA-256 and the username, and combined with a non-short-circuiting
`&` so timing does not reveal which half was wrong. API keys are 192 bits,
shown once, stored hashed (with a test asserting the plaintext is not in the
file). `Throttle` counts in-flight attempts as failures, so parallel requests
cannot slip past `max_failures` (proved by a 40-way concurrent test); bans
double up to seven days; a dropped `Attempt` still counts, so hanging up
mid-check does not buy a free guess; one ban covers an IPv6 /64 and v4-mapped
addresses are folded to IPv4; the tracked-client table never evicts a record
that holds a ban or a live attempt; bans survive a server restart. Argon2 runs
behind a 2-permit semaphore on a blocking thread. Sessions are 128-bit, capped
at 32, idle-expired.

**`net::Gate` — sound.** The client policy runs on the accept loop before
anything else; TLS handshakes move to spawned tasks with a 10-second timeout and
a 32-permit semaphore, and new connections are turned away rather than queued
when it is full. `is_local_network` gets the ranges right, including
fc00::/7 and fe80::/10 and v4-mapped folding, and correctly treats CGNAT
100.64/10 as public. Anything arriving on the tunnel's own address is refused
even from a private peer. The certificate is generated once with an owner-only
key file, user PEM files are size-capped at 1 MiB, and rustls is configured with
safe default protocol versions and no client auth. `client_ip` handles
`X-Forwarded-For` the right way round — only when `reverse_proxy` is on and the
peer is a trusted proxy, taking the rightmost untrusted hop — though a
misconfigured proxy that forwards the header unchanged would let a client claim
`127.0.0.1`, which is the inherent hazard of the feature and is opt-in.
Mutating API calls require POST (`read` is tried first, then `act` only for
POST). Defaults are good: remote control off, both bypasses off, CSRF on,
secure cookies on, HTTPS on, `allow_public` off, UPnP off.

**Backups and sealed history — sound as designed.** `RIPTRBK\0` with
XChaCha20-Poly1305 and the full header (version, mode, salt, nonce) as AAD, so
no field can be swapped; version and mode are validated before use; the deflate
payload is bounded with `.take(MAX_PLAINTEXT_BYTES + 1)` and re-checked, so a
zip bomb cannot balloon memory past 512 MiB; Argon2id at the OWASP baseline for
password mode. `history.rs` is the same construction with the header as AAD, a
file-size bound, no compression, and `sanitize()` after deserialising; an
unreadable key makes history read-only for the session and leaves the file
alone. The one thing to keep in mind is that mode 0 is forgeable by design,
which is what A1 is about.

**Restore validation, apart from settings — sound.** `restore_torrent`
re-parses the `.torrent`, insists its info hash matches the record's claim,
caps it at `MAX_TORRENT_BYTES`, strips control characters from the name, drops
unknown categories, revalidates and truncates tags, range-checks `renames` and
`file_priority` against the real file count and re-runs `clean_rel_path` on
every rename, runs `check_root` on the save folder and `move_on_complete`, and
clears `checksums`, `findings`, `content_findings` and `queue_pos` because a
forged backup could claim files were verified or hide warnings. `only_files`
indices are bounds-checked.

**RSS parsing — sound.** 4 MiB feed cap, 1000 items, depth 64, 64 KiB per text
node, 500-char titles, 8 KiB links rejected if they contain control or
whitespace characters, and entities resolved from a fixed allowlist
(`resolve_entity`) rather than expanded — so a billion-laughs document stays
small, which the module's own test asserts.

**Web seeds — sound.** `fetch_range` computes the wanted byte count up front and
takes only `want - out.len()` from each chunk, so a server that streams more
than it was asked for cannot grow the buffer; `Content-Range` must match the
requested range exactly; HTTP 200 is only accepted when the range starts at 0;
`host_allowed` keeps private and loopback addresses out unless the test hook
allows them; every request is recorded in the ledger. The only concern is the
unbounded piece length feeding `Vec::with_capacity`, folded into A3.

**IPC surface — in sync, no mismatch in either direction.** All three lists
hold exactly the same 118 commands: `#[tauri::command]` functions in
`src-tauri/src/commands.rs`, the `generate_handler!` list in
`src-tauri/src/lib.rs`, and `APP_COMMANDS` in `isolation/index.js`. The
isolation hook is default-deny and rejects a non-string `cmd`; the plugin
prefixes are limited to `event`, `window`, `webview`, `app` and `path`, and the
only explicit plugin commands are the five dialog ones — no opener,
notification or deep-link permission, as `CLAUDE.md` requires.

**`unsafe` placement — exactly as `CLAUDE.md` specifies.** Enumerated in full
under A5, together with a soundness review of each permitted block. The only
issue is that the `riptor` crate does not enforce the rule.

# What this audit did not cover

- **The full gate did not run locally.** `cargo clippy --workspace
  --all-targets` and `cargo test --workspace` cannot complete on this machine:
  the default toolchain is MSVC with no MSVC linker, and under the MinGW
  toolchain `tauri-winres` fails because `windres` cannot handle the space in
  the `Intern Project` path (`cc1.exe: fatal error: Project\riptor\...: No such
  file or directory`). Library crates build and test fine; the `riptor` and
  `riptor-vpn-helper` binaries do not. CI covers both, and CI is reported
  green. This is an environment limitation, not a finding, but it means the
  UI-side and binary-side lints here rest on CI.
- **Linux-only behaviour was read, not run**: the bubblewrap sandbox, the
  pkexec flow and `elevate::tty`, the WireGuard path, `netinfo.rs`, and the
  headless daemon. `CLAUDE.md` already lists testing these on real Linux as
  outstanding work; this audit does not change that.
- **`.tsx` vitest component suites** were skipped, as instructed (they fail
  locally for an unrelated undici reason).
- **Not re-audited in depth**, having been read only for the specific questions
  above: `engine.rs`'s 3326 lines as a whole, the seeding scheduler, the
  checksum/suspicion job machinery, `import.rs`, `geoip.rs`, the MSE/PE
  implementation in `vendor/librqbit/src/mse.rs`, and the UDP scrape parser
  beyond its length checks. The `tick()` and saver races the brief asked about
  were looked at through `relocate.rs` and the `move`/`reattach` path (A4); a
  focused review of `saver.rs` ordering against `tick()` is still worth doing.
- **No upgrade was applied.** Part 1 reports; it changes nothing.
